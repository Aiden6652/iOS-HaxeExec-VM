# x86_64 模拟性能实测 —— 决定是否继续立项

方法：同一份 `bench/workloads.c` 编两次，一次 `-nostdlib -static` 出 ELF 放进 Unicorn 跑，
一次编成宿主原生 `.so` 直接调用，同样入参取墙钟比。**所有 workload 结果校验一致（全部 ✅）**。
机器：Linux x86_64，Unicorn 2.1.4（QEMU TCG）。

## 一、归因：慢在哪

| 操作形态 | 原生 | 模拟 | 折损 |
|---|---:|---:|---:|
| 纯寄存器算术（不访存） | 0.27 ms | 0.29 ms | **x1.1** |
| 1× int64 读 | 11.1 ms | 41.2 ms | x3.7 |
| 4× int64 读 | 23.4 ms | 80.2 ms | x3.4 |
| 8× int64 读 | 20.7 ms | 141.1 ms | x6.8 |
| 4× double 读 | 18.0 ms | 391.2 ms | x21.8 |
| 4× int64 **写** | 28.3 ms | 1196.3 ms | **x42.2** |
| 4 读 + 4 写 int64 | 14.5 ms | 1165.8 ms | **x80.6** |
| 4× double **写** | 20.2 ms | 1546.7 ms | **x76.5** |

翻译器本身几乎不慢（纯寄存器 **1.1x**）。代价全在**访存**：Unicorn 走 soft-MMU，
每条来宾访存指令要进 helper + TLB 查表，而**写比读贵一个数量级**（要标脏 + 失效检查）。

## 二、套到真实 workload

| workload | 原生 | 模拟 | 折损 |
|---|---:|---:|---:|
| 指针追逐（工作集在 L1） | 36.3 ms | 100.5 ms | x2.8 |
| 指针追逐（8MB） | 21.2 ms | 185.3 ms | x8.8 |
| 链表遍历，每节点只读 1 字段 | 116.0 ms | 400.4 ms | x3.5 |
| DisplayObject 链表逐帧 update（6 字段，含写） | 113.3 ms | 11397 ms | **x100.6** |
| 同上，8 字段 | 112.8 ms | 14345 ms | **x127.2** |
| UTF-16 资源 key hash | 120.8 ms | 315.4 ms | x2.6 |
| 精灵 4x4 transform 合成 | 120.8 ms | 14887 ms | **x123.2** |
| 32 路 PCM 混音 | 5.7 ms | 149.2 ms | x26.3 |

VM 退出代价实测 **111 µs / 次**，但这是 Python 绑定下的数字，C++ 宿主会低 1~2 个数量级，
仍然会是主要成本之一。

## 三、对 60fps 目标的判决

hxcpp 生成的代码形态就是**密集的堆对象字段读改写**（每个 Sprite 每帧几十次 load/store），
正好踩中 soft-MMU 最贵的路径，实测 **40~130 倍**折损。

换算帧预算：一帧原生 4 ms → 模拟后 160~520 ms → **2~6 fps**。这还没算渲染 API 转发的 VM 退出、
 iOS 本机相对这台 32 核服务器的单核差距、以及 x86_64→ARM64 比同构翻译更大的展开比。

> **判决：Unicorn 路线下 60fps 不可达，差距是数量级而不是百分比。**

## 四、如果还要走 VM 路线

根因不是"选错引擎"，是**选错了内存模型**：

| | Unicorn（当前） | qemu-user / Box64 式 dynarec |
|---|---|---|
| 来宾访存 | soft-MMU，每次都过 helper | 来宾内存**直接映射**进宿主地址空间 |
| load/store 成本 | x3 ~ x80 | ≈ 原生单条指令 |
| 预期整体折损 | x40 ~ x130 | x3 ~ x8 |

把核心换成**直接映射式 dynarec**（Box64 移植到 Darwin，或裁剪过的 qemu-user）才可能压到个位数——
那时是 10~20fps 而不是 2fps，但依然不是 60。

## 五、能真正锁 60fps 的替代路线

Psych Engine 的资源全是标准格式：JSON 谱面、PNG/XML 精灵表、OGG 音轨，大部分就躺在 exe 旁边的
`assets/`，没打包进二进制。把它们喂给**原生支持 iOS 的 Haxe 引擎**（Codename Engine 官方就有
iOS/Android 构建目标，Psych 也有社区移动分支），逻辑与渲染走 Metal，60fps 没有悬念。

- 优点：真·60fps、判定延迟可控、上架合规风险低得多。
- 代价：被魔改的逻辑要重做（谱面/判定好还原，UI 与自定义脚本是大头）。

## 六、下一步（二选一）

1. **继续 VM**：先把内核从 Unicorn 换成直接映射 dynarec 原型，验证能否把「写」压到个位数折损。
2. **转向移植**：先把资源提取 pipeline 打通，跑通「原始资源 + 原生移动端引擎」版本。
